# 동시성 제어 전략

본 프로젝트는 여러 사용자가 동시에 주문하거나 포인트를 충전할 수 있으며, 애플리케이션이 여러 서버 또는 여러 인스턴스로 실행되는 환경을 고려합니다.

따라서 JVM 내부의 동기화만으로는 충분하지 않으며, 여러 인스턴스에서 공유할 수 있는 데이터베이스 수준의 동시성 제어를 중심으로 설계합니다.

---

# 1. 동시성 제어가 필요한 데이터

본 프로젝트에서 동시에 여러 요청이 접근할 수 있는 주요 데이터는 다음과 같습니다.

- 메뉴 재고
- 사용자 포인트
- 주문 생성
- 동일한 주문 요청의 중복 처리

각 문제는 서로 다른 성격을 가지므로 하나의 동시성 제어 방식으로 해결하지 않습니다.

| 대상 | 발생 가능한 문제 | 주요 대응 |
|---|---|---|
| 메뉴 재고 | 동시에 주문하여 재고 초과 차감 | DB 비관적 락 |
| 사용자 포인트 | 동시에 결제하여 잔액 오류 | DB 낙관적 락 |
| 동일 주문 요청 | 같은 요청이 여러 번 처리 | 멱등성 |
| 주문 + 포인트 + 재고 | 일부 작업만 성공 | DB Transaction |
| 여러 서버/인스턴스 | JVM별 락이 서로 공유되지 않음 | DB 수준 제어 |

---

# 2. 멀티 인스턴스 환경을 고려한 동시성 제어

애플리케이션이 하나의 서버에서만 실행된다고 가정하면 `synchronized`나 `ReentrantLock`과 같은 JVM 내부 락을 사용할 수 있습니다.

하지만 실제 운영 환경에서는 여러 서버 또는 여러 애플리케이션 인스턴스가 실행될 수 있습니다.

```text
              Load Balancer
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
      Instance 1 Instance 2 Instance 3
          │         │         │
          └─────────┼─────────┘
                    ↓
                  MySQL
```

각 인스턴스는 서로 다른 JVM에서 실행되기 때문에 JVM 내부 락은 다른 인스턴스의 요청까지 제어할 수 없습니다.

따라서 공유 데이터의 동시성 제어는 데이터베이스 수준에서 수행합니다.

```text
Instance 1 ──┐
Instance 2 ──┼──→ MySQL
Instance 3 ──┘
                 ↓
          DB 수준 동시성 제어
```

이를 통해 여러 서버에서 동시에 접근하더라도 동일한 데이터를 기준으로 동시성 제어가 가능합니다.

---

# 3. 메뉴 재고 동시성 제어

메뉴 재고는 동시에 여러 주문이 발생할 경우 가장 직접적으로 동시성 문제가 발생하는 데이터입니다.

예를 들어 특정 메뉴의 재고가 1개인 상황에서 두 명의 사용자가 동시에 주문할 수 있습니다.

```text
현재 재고 = 1

사용자 A → 아메리카노 1개 주문
사용자 B → 아메리카노 1개 주문
```

두 요청이 동시에 재고를 조회하고 차감하려고 하면 재고가 잘못 처리될 수 있습니다.

---

## 3.1 재고 동시성 제어 방식

재고는 주문 요청이 집중될 수 있고, 재고 수량의 정확성이 중요하기 때문에 DB 비관적 락을 사용합니다.

```text
사용자 A 요청
     ↓
메뉴 조회 + Row Lock
     ↓
재고 확인
     ↓
재고 차감
     ↓
COMMIT
     ↓
Lock 해제

사용자 B 요청
     ↓
메뉴 조회 대기
     ↓
A의 Transaction 종료
     ↓
메뉴 조회
     ↓
재고 확인
     ↓
재고 부족 → 주문 실패
```

비관적 락을 사용하면 먼저 해당 메뉴의 데이터를 점유한 트랜잭션이 작업을 완료할 때까지 다른 트랜잭션이 해당 데이터에 접근하여 변경하는 것을 제어할 수 있습니다.

---

## 3.2 재고 동시성 테스트

다음 상황을 테스트합니다.

```text
메뉴 재고 = 1

동시에 2개의 주문 요청
        ↓
┌───────┴───────┐
↓               ↓
주문 A          주문 B
1개 주문        1개 주문
↓               ↓
성공            실패
        ↓
최종 재고 = 0
```

검증 항목:

- 주문이 2건 모두 성공하지 않는가?
- 최종 재고가 음수가 되지 않는가?
- 실제 성공한 주문 수와 재고 차감 수가 일치하는가?
- 여러 서버에서 실행해도 동일한 결과가 나오는가?

---

# 4. 사용자 포인트 동시성 제어

포인트 역시 동시에 여러 요청이 접근할 수 있습니다.

예를 들어 사용자의 현재 포인트가 10,000P이고 동시에 두 주문이 발생한다고 가정합니다.

```text
현재 포인트 = 10,000P

주문 A → 8,000P 결제
주문 B → 5,000P 결제
```

두 요청이 동시에 현재 포인트를 조회한다면 각각 10,000P가 있는 것으로 판단할 수 있습니다.

따라서 단순히 애플리케이션에서 포인트를 조회한 후 차감하는 방식만으로는 동시성 문제를 해결할 수 없습니다.

---

## 4.1 포인트 동시성 제어 방식

포인트는 동시에 변경될 수 있는 사용자 데이터이므로 DB 낙관적 락을 적용합니다.

```text
User
├── id
├── point
└── version
```

포인트를 변경할 때 데이터의 버전을 함께 확인합니다.

```text
현재 User

point = 10,000
version = 1
```

두 요청이 동시에 데이터를 조회합니다.

```text
주문 A
point = 10,000
version = 1

주문 B
point = 10,000
version = 1
```

먼저 주문 A가 포인트를 변경합니다.

```text
주문 A
10,000 → 2,000
version 1 → 2
```

이후 주문 B가 기존 버전인 `1`을 기준으로 변경하려고 하면 버전이 이미 변경되었기 때문에 충돌이 발생합니다.

```text
주문 B
기대 version = 1
실제 version = 2

        ↓

Optimistic Lock 충돌
        ↓
주문 실패 또는 재시도
```

이를 통해 동시에 발생한 요청이 동일한 포인트 잔액을 기준으로 잘못 결제하는 것을 방지합니다.

---

# 5. 포인트 충전과 결제의 동시성

포인트 충전과 주문 결제가 동시에 발생하는 상황도 고려합니다.

예를 들어 사용자의 현재 포인트가 5,000P인 상황에서 다음 요청이 동시에 발생할 수 있습니다.

```text
현재 포인트 = 5,000P

요청 A → 5,000P 충전
요청 B → 8,000P 결제
```

두 요청이 동시에 `User.point`를 변경하기 때문에 동일한 사용자 포인트에 대한 동시성 제어가 필요합니다.

따라서 포인트를 변경하는 모든 작업에 동일한 DB 수준의 동시성 제어 정책을 적용합니다.

```text
포인트 충전 ──┐
              ├──→ User.point
포인트 결제 ──┘
                   ↓
             동시성 제어
```

포인트 충전 이력과 사용자 포인트 변경은 하나의 트랜잭션으로 처리하여 데이터 일관성도 함께 보장합니다.

---

# 6. 동일한 주문 요청의 중복 처리

동일한 주문 요청이 여러 번 전달되는 문제는 일반적인 동시성 문제와 구분해야 합니다.

예를 들어 사용자가 결제 버튼을 빠르게 두 번 클릭하거나 네트워크 오류로 클라이언트가 동일한 요청을 재전송할 수 있습니다.

```text
사용자
  ↓
주문 요청
  ├── 요청 A
  └── 요청 A 재전송
```

이 경우 단순히 락을 사용하는 것보다 **멱등성(Idempotency)**을 적용하는 것이 적절합니다.

---

## 6.1 멱등성 키 사용

클라이언트가 주문 요청에 고유한 `idempotencyKey`를 함께 전달하도록 구성합니다.

```json
{
  "idempotencyKey": "order-request-abc123",
  "userId": 1,
  "items": [
    {
      "menuId": 1,
      "quantity": 2
    }
  ]
}
```

동일한 `idempotencyKey`로 요청이 다시 들어오면 이미 처리된 요청인지 확인합니다.

```text
첫 번째 요청
    ↓
idempotencyKey 확인
    ↓
처리되지 않음
    ↓
주문 생성
    ↓
처리 완료 기록

두 번째 동일 요청
    ↓
idempotencyKey 확인
    ↓
이미 처리됨
    ↓
중복 주문 생성하지 않음
```

이를 통해 다음 작업이 중복 실행되는 것을 방지합니다.

- 주문 생성
- 포인트 차감
- 재고 차감
- 외부 데이터 전송 이벤트 생성

---

# 7. 주문 처리와 트랜잭션

주문 과정에서 포인트, 재고, 주문 데이터를 각각 독립적으로 처리하면 일부 작업만 성공하는 문제가 발생할 수 있습니다.

따라서 DB 내부에서 함께 성공하거나 실패해야 하는 작업은 하나의 트랜잭션으로 처리합니다.

```text
주문 요청
   ↓
재고 확인
   ↓
포인트 확인
   ↓
┌──────────────────────────┐
│       Transaction        │
│                          │
│ 포인트 차감              │
│ 재고 차감                │
│ Order 저장               │
│ OrderItem 저장           │
│ Outbox 저장              │
│                          │
└────────────┬─────────────┘
             ↓
           COMMIT
```

중간에 하나라도 실패하면 전체 작업을 롤백합니다.

```text
포인트 차감 성공
      ↓
재고 차감 성공
      ↓
Order 저장 성공
      ↓
OrderItem 저장 실패
      ↓
    ROLLBACK
      ↓
전체 변경사항 취소
```

---

# 8. 락 획득 순서

하나의 주문에서 여러 데이터에 락을 획득해야 하는 경우 락을 획득하는 순서를 일관되게 유지합니다.

예를 들어 주문 처리에서 다음 순서를 사용한다고 가정합니다.

```text
1. Menu Lock
2. User Lock
3. 데이터 변경
4. COMMIT
```

모든 주문 요청이 동일한 순서로 락을 획득하도록 합니다.

```text
주문 A
Menu → User

주문 B
Menu → User
```

반대로 다음처럼 서로 다른 순서로 락을 획득하면 데드락이 발생할 가능성이 높아집니다.

```text
주문 A
Menu → User

주문 B
User → Menu
```

따라서 여러 데이터에 대한 락이 필요한 경우 락 획득 순서를 일관되게 유지합니다.

---

# 9. 비관적 락과 낙관적 락 선택 기준

본 프로젝트에서는 모든 데이터에 동일한 락 방식을 적용하지 않습니다.

데이터의 특성과 충돌 가능성을 기준으로 선택합니다.

### 메뉴 재고 → 비관적 락

재고는 주문 요청이 동시에 집중될 수 있고, 재고 초과 판매를 방지하는 것이 중요합니다.

따라서 실제 주문 처리 시 해당 메뉴 데이터를 잠그고 처리하는 비관적 락을 사용합니다.

```text
Menu
 ↓
Pessimistic Lock
 ↓
재고 확인
 ↓
재고 차감
```

### 사용자 포인트 → 낙관적 락

포인트는 동시에 변경될 수 있지만 일반적인 요청에서는 충돌이 발생하지 않을 수 있습니다.

따라서 변경 시점에 충돌을 감지하는 낙관적 락을 적용합니다.

```text
User
 ↓
Optimistic Lock
 ↓
포인트 변경
 ↓
version 확인
 ↓
충돌 시 실패 또는 재시도
```

---

# 10. Redis 분산 락을 사용하지 않는 이유

애플리케이션이 여러 인스턴스로 실행되더라도 모든 동시성 문제에 Redis 분산 락이 필요한 것은 아닙니다.

본 프로젝트에서는 핵심 데이터인 포인트와 재고가 MySQL에서 관리되므로 DB 수준의 동시성 제어를 우선적으로 사용합니다.

```text
Instance 1 ──┐
Instance 2 ──┼──→ MySQL
Instance 3 ──┘
                  ↓
            DB Lock / Version
```

Redis는 인기 메뉴 조회 및 집계를 위한 저장소로 사용하며, 단순히 여러 서버에서 실행된다는 이유만으로 별도의 Redis 분산 락을 추가하지 않습니다.

필요 이상의 분산 락을 사용하면 락 획득 및 해제 실패, 장애 처리, 타임아웃 등 추가적인 복잡성이 발생할 수 있기 때문에 실제로 필요한 동시성 문제에 대해서만 락을 적용합니다.

---

# 11. 동시성 테스트 전략

동시성 제어가 실제로 동작하는지 검증하기 위해 동시에 여러 요청을 실행하는 테스트를 작성합니다.

## 11.1 재고 경쟁 테스트

조건:

```text
메뉴 재고 = 1
주문 요청 = 2건
각 주문 수량 = 1
```

기대 결과:

```text
성공 주문 = 1건
실패 주문 = 1건
최종 재고 = 0
```

검증:

- 재고가 음수가 되지 않는가?
- 재고보다 많은 주문이 성공하지 않는가?
- 최종 재고가 실제 주문 수와 일치하는가?

---

## 11.2 포인트 경쟁 테스트

조건:

```text
사용자 포인트 = 10,000P

주문 A = 8,000P
주문 B = 5,000P
```

기대 결과:

```text
성공 주문 = 최대 1건
최종 포인트 >= 0
```

검증:

- 포인트가 음수가 되지 않는가?
- 두 주문이 모두 성공하지 않는가?
- 포인트 차감 금액이 실제 성공한 주문과 일치하는가?

---

## 11.3 동일 요청 중복 테스트

조건:

```text
동일 idempotencyKey
동일 주문 요청
동시에 여러 번 요청
```

기대 결과:

```text
주문 생성 = 1건
포인트 차감 = 1회
재고 차감 = 1회
```

---

## 11.4 멀티 인스턴스 테스트

실제 여러 애플리케이션 인스턴스를 실행한 환경에서 동일한 동시성 시나리오를 테스트합니다.

```text
             Load Balancer
                   ↓
        ┌──────────┼──────────┐
        ↓          ↓          ↓
    Instance 1 Instance 2 Instance 3
        │          │          │
        └──────────┼──────────┘
                   ↓
                 MySQL
```

검증 대상:

- 여러 인스턴스에서 동시에 주문해도 재고가 정확하게 차감되는가?
- 여러 인스턴스에서 동시에 결제해도 포인트가 정확하게 차감되는가?
- 동일 요청이 여러 인스턴스로 전달되어도 중복 주문이 발생하지 않는가?

# 12. 동시성 제어 전략 요약

| 상황 | 문제 | 해결 전략 |
|---|---|---|
| 동일 메뉴 동시 주문 | 재고 초과 차감 | 비관적 락 |
| 동일 사용자 동시 결제 | 포인트 중복 차감 | 낙관적 락 |
| 포인트 충전 + 결제 동시 발생 | `User.point` 동시 수정 | DB 동시성 제어 |
| 동일 주문 요청 재전송 | 중복 주문 | 멱등성 키 |
| 주문 처리 중 일부 작업 실패 | 부분 성공 | DB Transaction |
| 여러 서버에서 동시 요청 | JVM 락 공유 불가 | DB 수준 동시성 제어 |
| 여러 데이터 락 획득 | 데드락 가능성 | 락 획득 순서 통일 |

# 13. 핵심 원칙

본 프로젝트의 동시성 제어는 다음 원칙을 기준으로 설계합니다.

1. JVM 내부 락이 아닌 공유 데이터베이스를 기준으로 동시성을 제어합니다.
2. 재고는 초과 판매 방지를 위해 비관적 락을 적용합니다.
3. 사용자 포인트는 변경 충돌을 감지하기 위해 낙관적 락을 적용합니다.
4. 동일한 요청이 반복되는 문제는 락이 아닌 멱등성으로 해결합니다.
5. 포인트, 재고, 주문 데이터의 변경은 하나의 DB 트랜잭션으로 묶습니다.
6. 여러 데이터에 락을 적용할 경우 락 획득 순서를 통일하여 데드락 가능성을 줄입니다.
7. 멀티 인스턴스 환경에서도 동일한 동시성 제어가 적용될 수 있도록 DB 수준의 제어 방식을 사용합니다.
8. 실제 구현 후 동시성 테스트와 멀티 인스턴스 테스트를 통해 설계가 의도대로 동작하는지 검증합니다.
