# 비즈니스 규칙

본 문서는 커피 주문 시스템의 주요 기능과 데이터 처리에 적용되는 비즈니스 규칙을 정의합니다.

---

# 1. 사용자 및 포인트

## 1.1 사용자 식별

- 사용자는 고유한 `userId`를 가집니다.
- 포인트 충전 및 주문 시 `userId`를 통해 사용자를 식별합니다.
- 존재하지 않는 사용자는 포인트를 충전하거나 주문할 수 없습니다.


### 사용자 식별 전제

본 과제에서는 인증 및 로그인 기능을 구현 범위에서 제외한다.

따라서 사용자 식별이 필요한 API에서는 요청으로 전달된 `userId`를 인증된 사용자의 ID라고 가정한다.

실제 인증/인가 환경에서는 인증 정보를 통해 현재 로그인한 사용자의 ID를 확인하고, 요청 대상 사용자와 일치하는지 검증해야 한다.

---

## 1.2 포인트 충전

- 포인트는 현금 금액과 동일한 단위로 충전합니다.
- **1원 = 1P**로 계산합니다.
- 포인트는 여러 번 충전할 수 있습니다.
- 충전 금액은 **0보다 커야 합니다.**
- 충전 요청이 성공하면 사용자의 현재 포인트가 충전 금액만큼 증가합니다.
- 충전 내역은 `charges` 테이블에 저장합니다.
- 충전 내역 저장과 사용자 포인트 증가는 하나의 트랜잭션으로 처리합니다.
- 충전 과정에서 하나의 작업이라도 실패하면 전체 작업을 롤백합니다.

### 예시

```text
현재 포인트 = 5,000P

10,000원 충전
      ↓
현재 포인트 = 15,000P
```

---

## 1.3 포인트 사용

- 주문 결제는 포인트만 사용할 수 있습니다.
- 주문 금액보다 보유 포인트가 부족하면 주문할 수 없습니다.
- 주문이 성공하면 주문 금액만큼 포인트를 차감합니다.
- 포인트는 음수가 될 수 없습니다.
- 동시에 여러 주문이 발생할 수 있으므로 포인트 차감 과정에서는 동시성 제어를 적용합니다.

### 예시

```text
현재 포인트 = 15,000P
주문 금액 = 10,000원

주문 성공
      ↓
남은 포인트 = 5,000P
```

---

# 2. 메뉴

## 2.1 메뉴 정보

메뉴는 다음 정보를 가집니다.

- 메뉴 ID
- 메뉴 이름
- 메뉴 가격
- 재고

메뉴의 현재 가격은 `menus.price`를 기준으로 합니다.

---

## 2.2 메뉴 목록 조회

- 사용자는 판매 중인 메뉴 목록을 조회할 수 있습니다.
- 메뉴 목록 조회 시 다음 정보를 제공합니다.
    - 메뉴 ID
    - 메뉴 이름
    - 메뉴 가격
- 메뉴 조회는 데이터를 변경하지 않는 조회 기능입니다.

---

## 2.3 메뉴 재고

- 메뉴는 재고 수량을 관리합니다.
- 주문 수량보다 재고가 부족하면 주문할 수 없습니다.
- 주문이 성공하면 주문 수량만큼 재고를 차감합니다.
- 재고는 음수가 될 수 없습니다.
- 여러 사용자가 동시에 동일한 메뉴를 주문할 수 있으므로 재고 차감 과정에서는 동시성 제어를 적용합니다.

### 예시

```text
메뉴 재고 = 5

3개 주문
      ↓
주문 성공
      ↓
메뉴 재고 = 2
```

재고가 2개인데 3개를 주문하는 경우:

```text
메뉴 재고 = 2
주문 수량 = 3

      ↓

재고 부족
      ↓
주문 실패
```

---

# 3. 주문

## 3.1 주문 기본 규칙

- 한 사용자는 여러 번 주문할 수 있습니다.
- 하나의 주문에는 하나 이상의 메뉴가 포함될 수 있습니다.
- 주문 시 사용자의 `userId`를 통해 주문자를 식별합니다.
- 존재하지 않는 사용자는 주문할 수 없습니다.
- 존재하지 않는 메뉴는 주문할 수 없습니다.
- 주문 수량은 0보다 커야 합니다.
- 주문 금액은 주문 당시의 메뉴 가격과 수량을 기준으로 계산합니다.

---

## 3.2 주문 금액 계산

주문 금액은 각 메뉴의 주문 당시 가격과 수량을 곱한 값의 합으로 계산합니다.

```text
메뉴 A
가격 = 3,000원
수량 = 2

메뉴 B
가격 = 4,000원
수량 = 1

총 주문 금액
= (3,000 × 2) + (4,000 × 1)
= 10,000원
```

---

## 3.3 주문 처리 순서

주문은 다음과 같은 흐름으로 처리합니다.

```text
사용자 확인
    ↓
메뉴 확인
    ↓
재고 확인
    ↓
주문 금액 계산
    ↓
포인트 확인
    ↓
포인트 차감
    ↓
재고 차감
    ↓
Order 저장
    ↓
OrderItem 저장
    ↓
주문 완료
```

포인트 차감, 재고 차감, 주문 저장 등 DB 내부에서 함께 성공해야 하는 작업은 하나의 트랜잭션으로 처리합니다.

---

## 3.4 주문 성공 조건

주문이 성공하기 위해서는 다음 조건을 모두 만족해야 합니다.

- 존재하는 사용자여야 합니다.
- 주문할 메뉴가 존재해야 합니다.
- 주문 수량이 유효해야 합니다.
- 메뉴의 재고가 충분해야 합니다.
- 사용자의 포인트가 주문 금액 이상이어야 합니다.
- 주문 및 결제 처리 과정에서 DB 오류가 발생하지 않아야 합니다.

하나라도 조건을 만족하지 못하면 주문은 실패합니다.

---

# 4. 주문 당시 메뉴 정보 보존

메뉴의 가격이나 이름은 주문 이후 변경될 수 있습니다.

따라서 주문 당시의 메뉴 정보를 `OrderItem`에 스냅샷으로 저장합니다.

```text
현재 Menu

아메리카노
가격 = 3,000원
       ↓
     주문
       ↓
OrderItem

menuName = 아메리카노
menuPrice = 3,000원
quantity = 2
```

이후 메뉴 가격이 변경되더라도 기존 주문의 메뉴 가격은 변경되지 않습니다.

### 예시

```text
주문 당시
아메리카노 = 3,000원

        ↓

메뉴 가격 변경

        ↓

현재 메뉴 가격 = 4,000원
```

기존 주문은 계속 다음 정보를 유지합니다.

```text
OrderItem.menuPrice = 3,000원
```

이를 통해 과거 주문 데이터를 주문 당시의 상태 그대로 보존합니다.

---

# 5. 주문 데이터 일관성

주문 과정에서 다음 데이터는 서로 일관된 상태를 유지해야 합니다.

- 사용자 포인트
- 메뉴 재고
- Order
- OrderItem

따라서 다음 작업은 하나의 DB 트랜잭션으로 처리합니다.

```text
┌────────────────────────────┐
│       DB Transaction       │
│                            │
│  포인트 차감               │
│  재고 차감                 │
│  Order 저장                │
│  OrderItem 저장            │
│                            │
└────────────────────────────┘
```

중간에 하나라도 실패하면 전체 작업을 롤백합니다.

### 예시

```text
포인트 차감 성공
      ↓
재고 차감 성공
      ↓
Order 저장 성공
      ↓
OrderItem 저장 실패
      ↓
    ROLLBACK
```

롤백 후에는 포인트와 재고 역시 주문 이전 상태로 복구되어야 합니다.

---

# 6. 중복 주문 방지

네트워크 오류나 사용자의 중복 클릭 등으로 동일한 주문 요청이 여러 번 전달될 수 있습니다.

따라서 주문 요청에는 멱등성을 적용하는 것을 고려합니다.

```text
동일 요청
   ↓
동일 idempotencyKey
   ↓
이미 처리된 요청인지 확인
   ↓
이미 처리됨
   ↓
중복 주문 생성하지 않음
```

동일한 요청이 중복으로 처리되지 않도록 하여 다음 작업의 중복 실행을 방지합니다.

- 주문 생성
- 포인트 차감
- 재고 차감
- 외부 데이터 전송

---

# 7. 외부 데이터 수집 플랫폼

주문이 성공적으로 완료되면 외부 데이터 수집 플랫폼으로 주문 데이터를 전달합니다.

전달 데이터에는 다음 정보를 포함할 수 있습니다.

- 사용자 식별자
- 메뉴 식별자
- 결제 금액
- 주문 식별자

```text
주문 완료
    ↓
주문 이벤트 생성
    ↓
외부 데이터 수집 플랫폼
```

외부 플랫폼과의 통신은 내부 DB 트랜잭션과 분리합니다.

외부 플랫폼의 장애가 내부 주문 데이터의 롤백을 직접 발생시키지 않도록 하며, 전달 실패에 대해서는 재시도 및 멱등성을 고려합니다.

# 8. 인기 메뉴

## 8.1 인기 메뉴 집계 기준

인기 메뉴는 **최근 7일 동안 발생한 주문 건수**를 기준으로 집계합니다.

여기서 주문 건수는 메뉴의 판매 수량이 아니라 해당 메뉴가 포함된 주문의 개수를 의미합니다.

### 예시

```text
주문 A
아메리카노 5개

주문 B
아메리카노 2개

주문 C
아메리카노 1개
```

아메리카노의 인기 메뉴 주문 건수는:

```text
3건
```

판매 수량인 `8개`가 아닙니다.

---

## 8.2 동일 주문 내 메뉴 수량 처리

하나의 주문에서 동일한 메뉴를 여러 개 주문하더라도 인기 메뉴 집계에서는 하나의 주문으로 계산합니다.

```text
주문 A
아메리카노 × 5
```

인기 메뉴 집계:

```text
아메리카노 주문 건수 = 1
```

---

## 8.3 인기 메뉴 기간

인기 메뉴는 조회 시점을 기준으로 최근 7일 동안의 주문을 대상으로 합니다.

```text
조회 시점
   ↓
최근 7일 범위
   ↓
해당 기간 내 주문 집계
```

7일보다 오래된 주문은 인기 메뉴 집계에서 제외합니다.

---

## 8.4 인기 메뉴 정렬 기준

인기 메뉴는 다음 우선순위로 정렬합니다.

1. 주문 건수 내림차순
2. 메뉴 가격 내림차순
3. 메뉴 ID 오름차순

```text
주문 건수 ↓
      ↓
가격 ↓
      ↓
메뉴 ID ↑
```

예를 들어 다음과 같은 데이터가 있다면:

| 메뉴 | 주문 건수 | 가격 |
|---|---:|---:|
| 아메리카노 | 100 | 3,000 |
| 카페라떼 | 100 | 4,000 |
| 바닐라라떼 | 100 | 4,000 |

정렬 결과:

```text
1. 카페라떼
2. 바닐라라떼
3. 아메리카노
```

가격까지 동일한 경우 메뉴 ID가 낮은 메뉴를 우선합니다.

---

## 8.5 인기 메뉴 반환 개수

인기 메뉴 조회 결과는 최대 3개까지 반환합니다.

```text
메뉴가 10개
    ↓
인기 메뉴 집계
    ↓
정렬
    ↓
TOP 3 반환
```

메뉴가 3개보다 적은 경우 존재하는 메뉴만 반환합니다.

---

# 9. 인기 메뉴 집계 처리

주문 완료 이벤트를 Kafka를 통해 전달하고 Consumer가 Redis에 인기 메뉴 집계 데이터를 반영합니다.

```text
주문 완료
    ↓
주문 완료 이벤트
    ↓
Kafka
    ↓
Consumer
    ↓
Redis 인기 메뉴 집계
    ↓
인기 메뉴 조회
```

주문 처리와 인기 메뉴 집계를 분리하여 주문 API의 처리와 조회 성능을 개선합니다.

인기 메뉴 집계는 비동기적으로 처리되므로 주문 완료 직후 일시적인 집계 지연이 발생할 수 있습니다.

따라서 인기 메뉴 데이터에는 최종 일관성을 적용합니다.

---

# 10. 동시성 관련 비즈니스 규칙

여러 사용자가 동시에 주문할 수 있으므로 다음 규칙을 적용합니다.

### 재고

- 재고보다 많은 주문이 동시에 성공해서는 안 됩니다.
- 재고는 음수가 될 수 없습니다.
- 동일 메뉴의 동시 주문에 대해 DB 수준의 동시성 제어를 적용합니다.

### 포인트

- 사용자의 보유 포인트보다 많은 금액을 동시에 결제할 수 없습니다.
- 포인트는 음수가 될 수 없습니다.
- 포인트를 변경하는 작업에 DB 수준의 동시성 제어를 적용합니다.

### 주문

- 동일한 주문 요청이 여러 번 처리되어 중복 주문이 생성되어서는 안 됩니다.
- 동일한 요청에 대해서는 멱등성을 보장합니다.

구체적인 동시성 제어 방식은 [동시성 제어 전략](concurrency.md)에서 정의합니다.

# 11. 비즈니스 규칙 요약

| 영역 | 규칙 |
|---|---|
| 사용자 | 고유한 `userId`를 가짐 |
| 포인트 충전 | 1원 = 1P |
| 포인트 충전 | 충전 금액은 0보다 커야 함 |
| 포인트 충전 | 여러 번 충전 가능 |
| 포인트 충전 | 충전 이력과 잔액 변경은 하나의 트랜잭션으로 처리 |
| 포인트 사용 | 주문 결제는 포인트만 사용 |
| 포인트 사용 | 주문 금액보다 포인트가 부족하면 주문 실패 |
| 메뉴 | 메뉴 ID, 이름, 가격, 재고를 관리 |
| 메뉴 재고 | 주문 수량보다 재고가 부족하면 주문 실패 |
| 메뉴 재고 | 주문 성공 시 주문 수량만큼 재고 차감 |
| 주문 | 한 사용자는 여러 번 주문 가능 |
