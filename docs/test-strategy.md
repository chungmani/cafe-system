# 테스트 전략

본 프로젝트에서는 단순한 기능 정상 동작뿐만 아니라 동시성, 데이터 일관성, 멱등성 및 다중 인스턴스 환경에서도 시스템이 비즈니스 규칙을 만족하는지 검증합니다.

테스트는 목적과 범위에 따라 단위 테스트, 통합 테스트, 동시성 테스트, 메시징 및 캐시 통합 테스트, 부하 테스트, 멀티 인스턴스 테스트로 구분합니다.

---

# 1. 테스트 목표

본 프로젝트의 테스트 목표는 다음과 같습니다.

1. 각 API가 정상적인 요청을 처리하는지 검증합니다.
2. 잘못된 입력과 예외 상황을 올바르게 처리하는지 검증합니다.
3. 트랜잭션 처리 과정에서 데이터가 부분적으로 변경되지 않는지 검증합니다.
4. 동시에 여러 요청이 발생해도 포인트와 재고가 정확하게 처리되는지 검증합니다.
5. 동일한 주문 요청이 중복 처리되지 않는지 검증합니다.
6. Kafka와 Redis를 이용한 인기 메뉴 집계가 정상적으로 동작하는지 검증합니다.
7. 여러 애플리케이션 인스턴스가 실행되는 환경에서도 데이터 일관성이 유지되는지 검증합니다.
8. 부하가 증가하더라도 시스템이 정상적으로 동작하는지 검증합니다.

---

# 2. 테스트 범위

본 프로젝트에서는 다음과 같은 테스트를 수행합니다.

| 테스트 유형 | 주요 검증 대상 |
|---|---|
| 단위 테스트 | 비즈니스 로직, 입력 검증, 계산 및 정렬 |
| 통합 테스트 | DB 연동, 트랜잭션, 실제 API 흐름 |
| 동시성 테스트 | 포인트 및 재고 동시 수정 |
| 멱등성 테스트 | 동일 주문 요청 중복 처리 |
| Kafka / Redis 통합 테스트 | 주문 이벤트 및 인기 메뉴 집계 |
| K6 부하 테스트 | 실제 HTTP 요청 기반 동시 부하 |
| 멀티 인스턴스 테스트 | 여러 서버 환경에서의 동시성 및 일관성 |

# 4. 포인트 충전 테스트

### 조건

```text

```

- `User.point`가 변경되지 않는가?

## 4.3 존재하지 않는 사용자

# 7. 주문 가격 스냅샷 테스트

메뉴 가격이 변경되더라도 주문 당시의 가격이 유지되는지 검증합니다.

### 테스트 과정

```text
메뉴 가격 = 3,000원
      ↓
주문
      ↓
OrderItem.menuPrice = 3,000원
      ↓
메뉴 가격 변경 = 4,000원
      ↓
기존 OrderItem.menuPrice 확인
```

### 검증

```text
OrderItem.menuPrice = 3,000원
```

현재 메뉴 가격이 변경되더라도 기존 주문의 가격이 변경되지 않아야 합니다.

- 최종 재고가 정확한가?
- 성공한 주문 수와 재고 차감 수량이 일치하는가?

---

```text

동시 주문 수량 총합 = 20
```

### 검증

- 최종 재고가 음수가 되지 않는가?

# 11. 주문 멱등성 테스트

# 12. 인기 메뉴 테스트

## 12.1 최근 7일 주문 집계

### 조건

최근 7일 이내 주문과 7일보다 오래된 주문을 함께 생성합니다.

### 검증

- 최근 7일 주문만 집계되는가?
- 7일보다 오래된 주문은 제외되는가?

---

## 12.2 주문 건수 기준 집계

다음과 같은 주문을 생성합니다.

```text
주문 A
아메리카노 × 5

주문 B
아메리카노 × 2
```

### 기대 결과

```text
아메리카노 주문 건수 = 2
```

판매 수량인 7이 아니라 주문 건수 2로 집계되어야 합니다.

---

## 12.3 동일 주문 내 수량 처리

### 조건

```text
주문 A
아메리카노 × 10
```

### 기대 결과

```text
아메리카노 주문 건수 = 1
```

수량이 아닌 주문 단위로 집계되는지 검증합니다.

---

## 12.4 인기 메뉴 정렬

다음 정렬 조건을 각각 테스트합니다.

```text
1순위 → 주문 건수 DESC
2순위 → 메뉴 가격 DESC
3순위 → 메뉴 ID ASC
```

### 검증

- 주문 건수가 높은 메뉴가 먼저 나오는가?
- 주문 건수가 같으면 가격이 높은 메뉴가 먼저 나오는가?
- 주문 건수와 가격이 모두 같으면 메뉴 ID가 낮은 메뉴가 먼저 나오는가?

---

## 12.5 TOP 3 검증

### 메뉴가 3개보다 많은 경우

```text

      ↓
```

# 16. K6 부하 테스트

기능 및 동시성 테스트에서 기본적인 정확성을 검증한 이후 실제 HTTP 요청을 이용한 부하 테스트를 수행합니다.

K6를 이용하여 다수의 사용자가 동시에 API를 호출하는 상황을 구성합니다.

---

## 16.1 주문 API 부하 테스트

### 목적

동시에 많은 주문 요청이 들어오는 상황에서 시스템의 안정성을 검증합니다.

### 검증 항목

- HTTP 응답 성공률
- 응답 시간
- 오류 발생률
- DB 커넥션 상태
- CPU 및 메모리 사용량
- 재고 정합성
- 포인트 정합성

---

## 16.2 재고 경쟁 부하 테스트

하나의 메뉴에 다수의 주문 요청을 동시에 전달합니다.

```text
메뉴 재고 = 100

동시 주문 요청
     ↓
K6
     ↓
여러 HTTP 요청
     ↓
여러 애플리케이션 인스턴스
     ↓
MySQL
```

### 검증

- 재고보다 많은 주문이 성공하지 않는가?
- 재고가 음수가 되지 않는가?
- 성공 주문 수량과 실제 재고 차감량이 일치하는가?

---

## 16.3 포인트 경쟁 부하 테스트

하나의 사용자에게 동시에 여러 주문 요청을 전달합니다.

### 검증

- 보유 포인트보다 많은 결제가 발생하지 않는가?
- 포인트가 음수가 되지 않는가?
- 최종 포인트가 정확한가?

---

## 16.4 중복 주문 부하 테스트

동일한 `idempotencyKey`를 여러 번 동시에 요청합니다.

### 검증

```text
동일 요청 100회
      ↓
실제 주문 = 1건
```

- 중복 주문이 발생하지 않는가?
- 포인트가 1회만 차감되는가?
- 재고가 1회만 차감되는가?

# 19. 핵심 테스트 원칙

본 프로젝트에서는 다음 원칙을 기준으로 테스트를 작성합니다.

1. 정상적인 기능 동작뿐만 아니라 실패 상황까지 테스트합니다.
2. DB 트랜잭션에 의해 데이터가 원자적으로 처리되는지 검증합니다.
3. 동시에 여러 요청이 발생했을 때 재고와 포인트의 정합성이 유지되는지 검증합니다.
4. 동일한 주문 요청이 중복 처리되지 않는지 검증합니다.
5. Kafka와 Redis를 통한 비동기 집계가 정상적으로 동작하는지 검증합니다.
6. 외부 플랫폼 전송 실패 및 재시도 상황을 검증합니다.
7. 여러 애플리케이션 인스턴스가 실행되는 환경에서도 동시성 제어가 정상적으로 동작하는지 검증합니다.
8. K6를 이용하여 실제 HTTP 요청 기반의 부하 상황을 검증합니다.
9. 테스트를 통해 기능의 정상 동작뿐만 아니라 데이터 일관성과 시스템의 안정성을 함께 검증합니다.
