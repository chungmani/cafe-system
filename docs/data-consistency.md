# 데이터 일관성 전략

본 프로젝트에서는 포인트, 재고, 주문 데이터가 서로 불일치하지 않도록 데이터베이스 트랜잭션을 중심으로 일관성을 보장합니다.

또한 외부 데이터 수집 플랫폼 및 인기 메뉴 집계처럼 데이터베이스 외부 시스템과 연동되는 작업은 하나의 DB 트랜잭션으로 처리할 수 없기 때문에, 이벤트 기반 처리와 재시도 및 멱등성을 고려합니다.

---

## 1. 데이터 일관성 목표

주문 및 결제 과정에서 다음 데이터가 서로 불일치하지 않는 것을 목표로 합니다.

- 사용자의 포인트 잔액
- 포인트 충전 이력
- 메뉴 재고
- 주문 정보
- 주문 상품 정보
- 주문 당시 메뉴 이름 및 가격
- 외부 데이터 수집 플랫폼에 전달되는 주문 데이터
- 인기 메뉴 집계 데이터

특히 주문 처리 과정에서는 다음 상태가 동시에 만족되어야 합니다.

```text
주문 성공
= 포인트 차감 성공
+ 재고 차감 성공
+ Order 저장 성공
+ OrderItem 저장 성공
```

하나라도 실패하면 주문 전체를 실패시키고 데이터베이스 변경사항을 롤백합니다.

---

# 2. 포인트 충전 데이터 일관성

포인트 충전은 다음 두 데이터를 함께 변경합니다.

- `users.point` 증가
- `charges` 충전 이력 저장

따라서 두 작업은 하나의 트랜잭션으로 처리합니다.

```text
포인트 충전 요청
      ↓
사용자 확인
      ↓
충전 금액 검증
      ↓
┌─────────────────────┐
│ DB Transaction      │
│                     │
│ 1. Charge 저장      │
│ 2. User.point 증가  │
│                     │
└─────────────────────┘
      ↓
    COMMIT
      ↓
충전 성공
```

### 성공하는 경우

```text
Charge 저장 성공
      +
User.point 증가 성공
      ↓
    COMMIT
```

두 작업이 모두 성공하면 트랜잭션을 커밋합니다.

### 실패하는 경우

```text
Charge 저장 성공
      ↓
User.point 증가 실패
      ↓
   ROLLBACK
      ↓
Charge 저장도 취소
```

반대로 `Charge` 저장 과정에서 실패하더라도 `User.point` 변경사항이 커밋되지 않도록 합니다.

이를 통해 다음과 같은 불일치를 방지합니다.

```text
충전 이력에는 10,000원이 존재
하지만 User.point에는 10,000P가 반영되지 않음
```

---

# 3. 주문 및 결제 데이터 일관성

주문 과정에서는 여러 데이터가 동시에 변경됩니다.

- 사용자 포인트 차감
- 메뉴 재고 차감
- `Order` 저장
- `OrderItem` 저장

따라서 이 작업들은 하나의 DB 트랜잭션으로 처리합니다.

```text
주문 요청
   ↓
사용자 확인
   ↓
메뉴 확인
   ↓
재고 확인
   ↓
주문 금액 계산
   ↓
포인트 확인
   ↓
┌─────────────────────────────┐
│ DB Transaction              │
│                             │
│ 1. 포인트 차감              │
│ 2. 재고 차감                │
│ 3. Order 저장               │
│ 4. OrderItem 저장           │
│                             │
└─────────────────────────────┘
   ↓
  COMMIT
   ↓
주문 성공
```

---

## 3.1 주문 처리 중 하나의 작업이 실패하는 경우

예를 들어 포인트 차감과 재고 차감은 성공했지만 `OrderItem` 저장 과정에서 오류가 발생하는 경우를 고려합니다.

```text
포인트 차감 성공
      ↓
재고 차감 성공
      ↓
Order 저장 성공
      ↓
OrderItem 저장 실패
      ↓
    ROLLBACK
```

롤백 후에는 다음 상태가 됩니다.

```text
포인트 → 원래 상태
재고   → 원래 상태
Order  → 저장되지 않음
OrderItem → 저장되지 않음
```

이를 통해 주문 데이터의 일부만 저장되는 상황을 방지합니다.

---

# 4. 메뉴 가격 데이터 일관성

메뉴의 가격은 주문 시점의 값을 보존해야 합니다.

현재 메뉴 가격이 변경되더라도 과거 주문의 가격이 변경되면 안 되기 때문에 `OrderItem`에 주문 당시의 메뉴 이름과 가격을 저장합니다.

```text
Menu
├── menuId
├── name
└── price
       ↓
   주문 시점
       ↓
OrderItem
├── menuId
├── menuName   ← 주문 당시 이름
├── menuPrice  ← 주문 당시 가격
└── quantity
```

예를 들어 메뉴 가격이 다음과 같이 변경되는 경우를 가정합니다.

```text
주문 당시
아메리카노 = 3,000원

        ↓

메뉴 가격 변경

        ↓

현재 아메리카노 = 4,000원
```

과거 주문의 `OrderItem.menuPrice`는 계속 3,000원으로 유지됩니다.

이를 통해 과거 주문 데이터를 조회했을 때 현재 메뉴 가격의 영향을 받지 않도록 합니다.

---

# 5. 재고 데이터 일관성

재고는 동시에 여러 주문이 들어올 수 있기 때문에 동시성 문제를 고려해야 합니다.

예를 들어 재고가 1개인 메뉴에 동시에 두 개의 주문이 들어오는 경우를 생각할 수 있습니다.

```text
현재 재고 = 1

주문 A → 1개 주문
주문 B → 1개 주문
```

두 요청이 동시에 재고를 확인하고 차감하면 재고가 잘못 처리될 수 있습니다.

따라서 재고 차감 과정에서는 DB 수준의 동시성 제어를 사용합니다.

```text
주문 A ──┐
         ├── 메뉴 재고 잠금
주문 B ──┘
         ↓
      재고 확인
         ↓
      재고 차감
         ↓
       COMMIT
```

재고가 부족한 주문은 실패하도록 하며, 최종적으로 재고가 음수가 되는 상황을 방지합니다.

구체적인 동시성 제어 방식은 [동시성 제어 전략](concurrency.md)에서 별도로 정의합니다.

---

# 6. 포인트 데이터 일관성

한 사용자가 동시에 여러 주문을 요청할 수 있기 때문에 `User.point`에 대한 동시성 문제도 고려합니다.

예를 들어 현재 포인트가 10,000P인 상황에서 동시에 다음 주문이 들어올 수 있습니다.

```text
주문 A → 8,000P 사용
주문 B → 5,000P 사용
```

두 요청이 동일한 포인트 잔액을 기준으로 결제를 진행하면 실제 보유 포인트보다 많은 금액이 차감될 수 있습니다.

따라서 포인트 차감 과정에서는 DB 수준의 동시성 제어를 적용합니다.

```text
현재 포인트
10,000P
   ↓
동시 요청 발생
   ├── 주문 A
   └── 주문 B
        ↓
DB 수준에서 동시 수정 제어
        ↓
정상적인 포인트 차감
```

구체적인 락 방식과 충돌 처리 방법은 [동시성 제어 전략](concurrency.md)에서 정의합니다.

# 7. 외부 데이터 수집 플랫폼과의 일관성

주문 완료 후 외부 데이터 수집 플랫폼으로 주문 데이터를 전달해야 합니다.

하지만 외부 HTTP 요청은 애플리케이션의 DB 트랜잭션에 포함할 수 없습니다.

따라서 다음과 같은 상황이 발생할 수 있습니다.

```text
DB 주문 처리 성공
      ↓
COMMIT
      ↓
외부 플랫폼 전송
      ↓
전송 실패
```

이 경우 DB에는 주문이 존재하지만 외부 플랫폼에는 주문 데이터가 전달되지 않는 문제가 발생합니다.

반대로 외부 플랫폼 전송이 먼저 성공한 후 DB 트랜잭션이 실패할 수도 있습니다.

```text
외부 플랫폼 전송 성공
      ↓
DB 저장 실패
      ↓
ROLLBACK
```

따라서 DB 트랜잭션과 외부 API 호출을 하나의 트랜잭션으로 묶지 않습니다.

---

# 8. Transactional Outbox 패턴

외부 데이터 수집 플랫폼과의 데이터 전달을 안정적으로 처리하기 위해 Transactional Outbox 패턴을 고려합니다.

주문 데이터와 외부 플랫폼으로 전달할 이벤트를 동일한 DB 트랜잭션에서 저장합니다.

```text
주문 요청
   ↓
┌──────────────────────────────┐
│ DB Transaction               │
│                              │
│ 1. Order 저장                │
│ 2. OrderItem 저장            │
│ 3. Outbox Event 저장         │
│                              │
└──────────────────────────────┘
   ↓
  COMMIT
   ↓
Outbox 이벤트 처리
   ↓
외부 데이터 수집 플랫폼 전송
```

주문과 Outbox 이벤트가 같은 트랜잭션으로 저장되기 때문에 주문 데이터가 저장되었지만 이벤트가 생성되지 않는 상황을 방지할 수 있습니다.

---

# 9. 외부 플랫폼 전송 실패 처리

외부 플랫폼으로 이벤트를 전달하는 과정에서 네트워크 오류나 외부 서버 장애가 발생할 수 있습니다.

이 경우 Outbox 이벤트를 삭제하지 않고 재시도할 수 있도록 구성합니다.

```text
Outbox 이벤트 조회
      ↓
외부 플랫폼 전송
      ↓
 ┌────┴────┐
성공       실패
 ↓          ↓
처리 완료   재시도
            ↓
       일정 횟수 재전송
```

이를 통해 일시적인 네트워크 장애가 발생하더라도 주문 데이터가 외부 플랫폼에 전달되지 않는 문제를 최소화합니다.

---

# 10. 외부 플랫폼 전송의 멱등성

재시도 과정에서 동일한 이벤트가 여러 번 전달될 수 있습니다.

예를 들어 다음과 같은 상황이 발생할 수 있습니다.

```text
주문 ID = 100

1차 전송 → 외부 플랫폼에서 처리 성공
             ↓
         응답 전달 실패

2차 전송 → 같은 주문 ID로 재전송
```

이 경우 외부 플랫폼에 동일한 주문이 두 번 기록될 수 있습니다.

따라서 외부 플랫폼이 지원한다면 `orderId`와 같은 고유한 식별자를 멱등성 키로 사용합니다.

```text
orderId = 100

첫 번째 요청
→ 처리

동일 orderId 요청
→ 이미 처리된 요청으로 판단
→ 중복 처리하지 않음
```

이를 통해 재시도에 따른 중복 데이터 생성을 방지합니다.

---

# 11. Kafka와 인기 메뉴 집계 데이터의 일관성

인기 메뉴 집계는 주문 처리와 분리하여 Kafka 이벤트 기반으로 처리합니다.

전체 흐름은 다음과 같습니다.

```text
주문 완료
   ↓
주문 완료 이벤트 발행
   ↓
Kafka
   ↓
Consumer
   ↓
Redis 인기 메뉴 집계 갱신
```

주문 자체의 성공 여부는 DB 트랜잭션으로 보장하고, 인기 메뉴 집계는 Kafka Consumer를 통해 비동기적으로 갱신합니다.

따라서 주문이 완료된 직후 인기 메뉴 조회를 수행하면 Redis 집계가 아직 반영되지 않았을 가능성이 있습니다.

이 구조에서는 주문 데이터와 인기 메뉴 집계 데이터 사이에 짧은 시간 차이가 발생할 수 있으며, 인기 메뉴 데이터는 최종적으로 일치하도록 구성합니다.

즉, 인기 메뉴 집계는 **강한 일관성보다 비동기 기반의 최종 일관성**을 적용합니다.

---

# 12. Redis 인기 메뉴 집계 실패 처리

Kafka Consumer가 주문 완료 이벤트를 정상적으로 소비하지 못하거나 Redis 갱신 과정에서 오류가 발생할 수 있습니다.

이 경우 Kafka의 메시지 재처리를 통해 Redis 집계를 다시 수행할 수 있도록 구성합니다.

```text
Kafka 이벤트
      ↓
Consumer
      ↓
Redis 갱신
      ↓
   실패
      ↓
메시지 재처리
      ↓
Redis 갱신 재시도
```

이를 통해 일시적인 Redis 장애가 발생하더라도 인기 메뉴 집계 데이터가 영구적으로 누락되지 않도록 합니다.

# 13. 데이터 일관성 전략 정리

| 대상 | 일관성 전략 | 목적 |
|---|---|---|
| `User.point` + `Charge` | DB Transaction | 포인트 잔액과 충전 이력 일치 |
| `User.point` + `Order` | DB Transaction | 결제와 주문 데이터 일치 |
| `Menu.stock` + `Order` | DB Transaction + 동시성 제어 | 재고와 주문 데이터 일치 |
| `Order` + `OrderItem` | DB Transaction | 주문 상세 데이터 일치 |
| `OrderItem` 가격 | 가격 스냅샷 | 주문 당시 가격 보존 |
| DB 주문 + 외부 플랫폼 | Transactional Outbox | 외부 전송 누락 방지 |
| 외부 플랫폼 재전송 | Idempotency Key | 중복 데이터 방지 |
| 주문 이벤트 + 인기 메뉴 | Kafka | 주문 처리와 집계 처리 분리 |
| Kafka + Redis | 재처리 / 재시도 | 인기 메뉴 집계 누락 방지 |
| 인기 메뉴 집계 | 최종 일관성 | 비동기 집계 구조 유지 |

---

# 14. 전체 데이터 흐름

```text
                         ┌───────────────┐
                         │   사용자 요청   │
                         └───────┬───────┘
                                 ↓
                         ┌───────────────┐
                         │   주문 처리    │
                         └───────┬───────┘
                                 ↓
              ┌─────────────────────────────────┐
              │          DB Transaction          │
              │                                 │
              │  User.point 차감                │
              │  Menu.stock 차감                │
              │  Order 저장                     │
              │  OrderItem 저장                 │
              │  Outbox Event 저장              │
              │                                 │
              └────────────────┬────────────────┘
                               ↓
                            COMMIT
                               ↓
                     ┌─────────┴─────────┐
                     ↓                   ↓
               Outbox 처리          주문 완료 이벤트
                     ↓                   ↓
             외부 플랫폼 전송          Kafka
                     ↓                   ↓
                  재시도             Consumer
                                         ↓
                                      Redis
                                         ↓
                                  인기 메뉴 조회
```

# 15. 핵심 원칙

본 프로젝트의 데이터 일관성은 다음 원칙을 기준으로 설계합니다.

1. 하나의 DB에서 함께 성공하거나 함께 실패해야 하는 작업은 하나의 트랜잭션으로 처리합니다.
2. 포인트와 재고처럼 동시에 변경될 수 있는 데이터는 DB 수준의 동시성 제어를 적용합니다.
3. 주문 당시의 메뉴 정보는 `OrderItem`에 스냅샷으로 저장합니다.
4. 외부 시스템과의 통신은 DB 트랜잭션과 분리합니다.
5. 외부 시스템 전송의 신뢰성을 높이기 위해 Transactional Outbox와 재시도를 고려합니다.
6. 재시도로 인한 중복 처리를 방지하기 위해 멱등성을 고려합니다.
7. 인기 메뉴 집계는 Kafka와 Redis를 이용한 비동기 처리로 구성하며 최종 일관성을 적용합니다.
